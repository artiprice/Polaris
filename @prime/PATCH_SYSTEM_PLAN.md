# Патч-система Polaris: решение и план

> Дата: 2026-10-28. Статус: предложение к согласованию. Основано на чтении текущего кода и обзоре
> Codex CLI, Claude Code, Aider, Cursor, OpenHands, Gemini CLI и Cline/Roo (ссылки в §5).

## 1. Решение: гибрид

**Ядро своё, парсинг и слияние — на проверенной библиотеке, форматы — те, что модели знают.**

| Слой | Решение | Почему |
|---|---|---|
| Ревизии, аренды, верификатор, атомарная запись, квитанции | **своё (уже есть)** | Ни одна библиотека и ни один конкурент не дают CAS-ревизий + Biscuit-аренд + трёхслойного верификатора. Это сильнейшая часть Polaris. |
| Поиск места правки | **своё: многоступенчатый матчер** | Codex, Cline и Gemini сошлись на одной схеме: точное совпадение → без хвостовых пробелов → без пробелов по краям → нормализация Unicode-пунктуации. Сейчас у нас только точное совпадение — главная причина провалов. |
| Разбор unified diff, перенос ханков со сдвигом, 3-way merge | **`diffy` 0.5.x** (MIT/Apache-2.0, маленькие зависимости, `no_std`) | Зрелый, умеет относительный поиск ханков и слияние с конфликт-маркерами. Самописный `patch.rs` (370 строк) это не умеет. `flickzeug` (форк с fuzzy) моложе, у него CLI-зависимости — только если `diffy` не хватит. |
| Посимвольное сохранение CRLF/LF и `\ No newline` | **своё (оставить из `patch.rs`)** | Байт-точность нужна для синхронизации в песочницы; `diffy` её не гарантирует. |
| Формат, который пишет модель | **search/replace (`edit_file`) — основной**, unified diff — для крупных правок, целый файл — для новых/малых | Независимые замеры (Aider, Diff-XYZ) показывают search/replace как самый надёжный формат для сильных моделей; Nemotron не обучен на V4A от Codex. |

Отвергнуто:
- **Взять чужой apply целиком** (git2/gix apply, flickzeug fs): теряем байт-точность и наши проверки, тянем C-зависимость (git2) или незрелый код.
- **Отдельная «apply-модель» как у Cursor**: нужна дообученная модель и GPU; несоразмерно для хакатона.
- **V4A как основной формат**: выгоден моделям OpenAI, а у нас Nemotron. Оставляем как возможный дополнительный формат после замеров (§4, этап 3).

## 2. Что есть сейчас (по коду)

- Инструменты правок в ядре (`crates/polaris-kernel/src/agent_tools.rs`): `write_file` (целый файл; при `expected_base: null` — создание), `edit_file` (точная замена, одна позиция или `replace_all`), `apply_patch` (unified diff **одного** файла), `file_revision` (CID текущих байт).
- Применение (`crates/polaris-tools/crates/builtin/src/patch.rs`): только точное совпадение контекста **и номера строки**; любой сдвиг → `Stale`. Нет fuzzy, нет поиска по смещению, нет толерантности к пробелам.
- Проверка: CID базы → аренда файла → `HybridMutationVerifier` (tree-sitter + метрики + S1) → одобрение → запись через temp + rename → квитанция в CAS.
- Пробелы: нет `delete_file`/`move_file`; нет транзакции на несколько файлов; `similar` объявлен в workspace, но не используется; каталог инструментов в `docs/tool-catalog.md` и схема в `builtin/registry.rs` расходятся со схемой ядра (там `expected_base` обязателен, `file_revision` отсутствует).
- **Отказы ломают кадр.** Неверные аргументы инструмента обрывали весь кадр; для read-only инструментов это исправлено 2026-10-28 (модель получает текст ошибки и повторяет вызов). Для мутирующего раннера (`KernelAgentToolRunner`) — ещё нет.

### Сделано 2026-10-29 (этап 1, часть)

- `polaris_tools::builtin::replace_text` — многоступенчатый матчер (`exact` → `trailing_whitespace` → `indentation` → `punctuation`), уникальность обязательна на каждом уровне, CRLF сохраняется, промах возвращает ближайшие строки файла с номерами. Используется и ядром (`frame_mutation.rs`), и builtin `edit_file`; раньше ядро при нескольких совпадениях молча правило первое.
- Уровень совпадения пишется в квитанцию мутации (`StoredReceipt` schema 2, поле `match_level`); верификатор кадра принимает schema 1 и 2.
- `KernelAgentToolRunner`: ошибки аргументов, промах `old_text`, устаревшая база и отказ верификатора возвращаются модели результатом вызова `{"status":"rejected","error","hint"}` (`ok: false`), кадр не обрывается; верификатор шага принимает такие результаты без изменений файлов.
- Осталось: `delete_file`/`move_file` (вместе с ChangeSet этапа 2), единая схема инструментов ядро = registry.

## 3. Целевое устройство

```
модель ──► edit_file / apply_patch / write_file / delete_file / move_file
              │
              ▼
        разбор (diffy для diff; JSON-схема для остальных)
              │
              ▼
        матчер: exact → rstrip → trim → unicode-punct   (уникальность обязательна)
              │  ── нет/неоднозначно ──► исправимая ошибка модели:
              │                          ближайший фрагмент + номера строк + похожесть
              ▼
        набор изменений (ChangeSet) по нескольким файлам, у каждого base CID
              │
              ▼
        аренды на все файлы ─► HybridMutationVerifier по каждому файлу и по набору
              │
              ▼
        одобрение ─► атомарная запись набора (staging + журнал отката) ─► квитанция
                                         └─ уровень fuzz записан в квитанцию
```

Правила:
1. **Уникальность прежде всего.** Ослабленный матчер применяется только если на своём уровне найдено ровно одно совпадение; иначе — исправимая ошибка со списком кандидатов.
2. **Fuzz виден.** Уровень совпадения (`exact`/`rstrip`/`trim`/`unicode`) пишется в квитанцию и показывается в UI-диффе; верификатор может требовать одобрения человека для неточных совпадений в чувствительных путях.
3. **Устаревшая база → 3-way merge, а не отказ.** Если файл изменился после `file_revision`, пробуем `diffy::merge(base, ours, theirs)`; без конфликтов — применяем с пометкой `rebased`, с конфликтами — исправимая ошибка с маркерами.
4. **Набор файлов атомарен.** Либо применяются все файлы ChangeSet, либо ни один (staging-копии, журнал, откат по Reaper при сбое).
5. **Ошибка — это подсказка.** Любой отказ, который модель может исправить, возвращается ей как результат вызова (как уже сделано для чтения); отказы политики (права, токен, scope) остаются жёсткими.

## 4. План работ

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **1. Надёжность (1–2 дня)** | Исправимые ошибки в `KernelAgentToolRunner`; многоступенчатый матчер в `edit_file`; `delete_file`, `move_file`; единая схема инструментов ядро = registry = `docs/tool-catalog.md` (генерация из одного источника) | тесты на каждый уровень матчера, на неоднозначность, на путь вне workspace; живой прогон: Nemotron правит файл в этом репозитории |
| **2. Diff и наборы (2–3 дня)** | `apply_patch` на `diffy` (+ наш байт-точный слой CRLF/LF); многофайловые патчи; ChangeSet с атомарной записью и откатом; rebase через `diffy::merge` | property-тесты (proptest) «apply(diff(a,b), a) == b» для CRLF/LF/BOM/без финального `\n`; тест отката при сбое на N-м файле |
| **3. Замер форматов (1–2 дня)** | Набор из ~50 задач правки по этому репозиторию; прогон Nemotron Lightning/Ultra и локальной модели на `edit_file` vs `apply_patch` vs целый файл; доля успеха, токены, число повторов | таблица результатов в `@prime/evidence`; формат по умолчанию выбирается по модели в конфиге |
| **4. UX (вместе с UI-этапом)** | Дифф в CLI/desktop/web с подсветкой уровня fuzz и rebase; одобрение по файлу и по набору; откат (`/undo`, `/rollback`) по квитанциям | ручная проверка сценария «правка → дифф → одобрение → откат» во всех трёх UI |

Зависимости: этапы 1–2 не требуют ключей; этап 3 требует провайдера (OpenRouter работает; дневной лимит бесплатных моделей — 50 запросов без кредитов, 1000 с кредитами от $5).
